## 一、这次真正修好的是什么

你反复说的「我都给你数据库了，还是播不了」——这次找到根因了，不是数据问题，是**番号口径对不上**。

### 根因

点一部作品时，App 要拿这部作品的番号去库里找它的播放地址。两边番号的写法不一样：

| 来自哪里 | 番号长什么样 |
|---|---|
| 作品卡片（库里 `videos.vod_id`） | `rki-6042` 小写、带横杠 |
| 兜底条目（`normalizeAvCode` 归一化） | `RKI6042` 大写、去横杠、去前导零 |

原来代码直接写 `entry.codeKey == work.codeKey` 比字符串——这两个**永远不可能相等**。

后果就是你看到的：
- 库里有 32 万条 m3u8 直链，**一条都用不上**；
- 点播放 → 拿不到库里的地址 → 回退去各站跨站爬 → 又慢又常失败 → 「点了播不了」。

### 改法

统一走 `normalizeAvCode` 归一化再比（`jsonEntriesForWorkCode`），两边口径一致。
库里的行本来就排在兜底池最前面，所以命中后第一个就是库里的直链，直接交给播放器开播，不再绕站源。

另外顺手修了两个同源问题：

1. **站点优先顺序失效**：作品记的站是 `whos.tv`（库里 `vod_play_from` 原样），计划侧站 id 是 `whos`，原来也不相等，导致「先探自己的站」这条策略一直没生效。现在过一层 `filmSiteId` 归一。
2. **先按「第 N 条」截断再匹配**：原来只在前 N 条（DB 行数）里挑，一旦顺序或去重有偏差就取不到。现在直接在整池里按归一化番号匹配。
